## Observed foundation and proposed module layout

T-1/T-3 have created only the paths marked observed. Create each remaining module when its owning task first needs it:

```text
src/
  app/                  Observed: Next.js root layout/page; later route/action edges
  modules/              Proposed: business capabilities used by web and worker
    identity/           Observed: atomic invitation acceptance; later auth/context policy
    counter/            Draft, quote, verification, and shipment operations
    provider/           Mengantar adapter and normalized provider results
    documents/          Immutable invoice and confirmed-label print preparation
    finance/            Read-only provider finance and estimated-profit views
    governance/         Branch/member lifecycle and JIT support
  db/                   Observed: foundation and T-3 identity/branch schemas; later shipment transactions
  worker/               Observed: always-on DB connectivity process; later outbox/reconciliation
  shared/               Small, dependency-safe types/helpers with actual cross-module use
drizzle/                Observed: reviewed foundation SQL migration and metadata
tests/                  Observed: DB and package compatibility tests; later browser tests
scripts/                Observed: synthetic seed and repository checks
docs/                   Canonical specifications, ADRs, and governance
```

Module-local unit tests and UI components may sit beside their owners; cross-module integration/browser tests belong in a clearly named test area. Generated framework/auth files follow their installed tool conventions and are reviewed before commit. Avoid an empty package workspace, duplicate web/worker copies of domain logic, or speculative packages. `public/`, configuration, and tool-specific directories are added only when the actual stack requires them.

## Dependency direction

| Caller | May depend on | Must not depend on |
|---|---|---|
| Browser UI in `app/` | Safe view models, components, validated action results | Database client, secrets, worker entry point, raw Mengantar adapter |
| Server route/action edge in `app/` | Auth/context resolution, domain operations, safe result translation | A second copy of business policy or direct provider dispatch |
| Domain module | Its own persistence port/queries and small shared contracts as needed | Next.js request/session globals or browser state as authority |
| `worker/` | Domain operation/claim logic, database and provider adapter | Next.js page/UI code or in-memory-only job state |
| Provider adapter | Verified Mengantar contract and server-only credentials | Client imports or unverified wire assumptions |

The actual dependency mechanism can be simple imports; this table does not require a dependency-injection framework. The present page is a server component with no client module or business data. ESLint restricts worker imports from UI routes; future browser modules must preserve the server-only boundary when added. Transactions, branch checks, state guards, money rules, and safe errors stay centralized under their owning modules/specifications. A circular dependency is a sign to move a shared contract to its real owner, not to add a new generic layer.
